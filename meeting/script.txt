Bonjour à tout le monde. On est The Library,
une équipe de 4 devs, et on est là pour vous présenter

Le contexte : on nous a donné une application Flask existante,
la "Librairie ABC". Une app de gestion de bibliothèque —

Sauf que cette app de départ elle était... disons,
fragile. Pas de sécurité, pas de tests, pas d'interface HTML.

Notre mission : la transformer en une vraie application web,
sécurisée, testée, et déployable en production.
On va vous montrer exactement comment on a fait ça sur 3 sprints.

  SLIDE 2 — ORGANISATION AGILE & GIT WORKFLOW       [RUDY ~2.5 min]
─────────────────────────────────────────────────────────────

Pour s'organiser, on a travaillé en Agile avec des sprints
d'une semaine. Trois sprints, trois objectifs clairs.

Sprint 1, semaine du 12 mai :
  analyse du code, identification des vulnérabilités,
  mise en place des premières fondations de tests.

Sprint 2, semaine du 19 mai :
  sécurisation concrète de l'app — headers HTTP, debug mode,
  authentification, hash des mots de passe.

Sprint 3, cette semaine :
  interface HTML complète avec Tailwind CSS,
  protection CSRF sur tous les formulaires,
  logging des actions sensibles.
  Et on est là pour vous présenter le résultat.

Côté Git, on a appliqué un workflow strict :
on ne touche jamais directement à main.
Chaque tâche = une issue GitHub, une branche dédiée,
une Pull Request relue par au moins un autre membre
avant de merger.

Tous les commits suivent le format conventionnel —
feat, fix, docs — avec le numéro d'issue en référence.
Ça donne un historique propre où on sait exactement
qui a fait quoi, quand et pourquoi.

─────────────────────────────────────────────────────────────
  SLIDE 3 — ANALYSE INITIALE & VULNÉRABILITÉS      [DIEGO ~3 min]
─────────────────────────────────────────────────────────────

Merci Rudy. Donc le code de départ,
avec Rudy on l'a passé en revue dès Sprint 1,
et on a dressé une liste de tout ce qui n'allait pas.

Côté architecture d'abord :
  - Zéro persistance des données. Tout était en mémoire.
    Au redémarrage de l'app, tout disparaissait.
  - Pas d'application Flask réelle, juste des classes Python brutes.
  - Pas d'authentification. N'importe qui pouvait réserver
    ou annuler n'importe quel livre sans s'identifier.
  - Pas de validation des entrées — un titre vide,
    une année négative, ça passait sans problème.

Côté sécurité, on a lancé Bandit —
l'outil d'analyse statique de sécurité Python.
Résultat : 13 vulnérabilités détectées. Les plus critiques :

  → Debug mode activé en production.
    Ça expose une console Python interactive dans le navigateur.
    Autant donner les clés du serveur à n'importe qui.

  → SECRET_KEY écrite en dur dans le code source.
    Si quelqu'un voit le code, il peut forger
    les cookies de session de tous les utilisateurs.

  → Zéro protection CSRF.
    N'importe quel site malveillant pouvait déclencher
    des actions au nom d'un utilisateur connecté
    sans qu'il s'en rende compte.

  → Pas de headers de sécurité HTTP.
    Clickjacking, XSS, content sniffing — rien n'était bloqué.

  → Zéro logging.
    Impossible de savoir qui avait fait quoi sur l'app.

On a tout documenté dans notre analyse de code,
et ça nous a servi de roadmap directe pour Sprint 2 et 3.

→ Ares, tu prends sur ce qu'on a mis en place côté tests ?

─────────────────────────────────────────────────────────────
  SLIDE 5 — CORRECTIONS & SÉCURITÉ                  [ARES ~3 min]
─────────────────────────────────────────────────────────────

Concrètement, voilà ce qu'on a implémenté.

Sprint 2 — sécurité de base :

  Debug mode : désactivé, contrôlé par variable d'environnement
  FLASK_DEBUG. En production il est à 0, point.

  Secret Key : générée avec os.urandom si pas définie.
  Cryptographiquement aléatoire. Elle ne touche jamais le code source.

  Headers de sécurité : X-Content-Type-Options, X-Frame-Options DENY,
  Content-Security-Policy — ajoutés sur toutes les réponses HTTP
  via un hook after_request. C'est une ligne de config,
  mais c'est ce qui empêche le clickjacking et le sniffing.

Sprint 3 — couche applicative :

  Authentification : Flask-Login pour les sessions,
  bcrypt pour les mots de passe.
  Même en cas de fuite de base de données,
  les hashs bcrypt sont pratiquement impossibles à inverser.
  Les routes sensibles ont un décorateur login_required.
  Les routes admin ont un décorateur admin_required custom
  qui retourne un 403 propre.

  CSRF : Flask-WTF avec un token caché dans chaque formulaire HTML.
  Les endpoints API JSON sont exemptés proprement —
  on passe les objets blueprint directement à csrf.exempt,
  pas des strings. Petite chose, mais ça marche pas autrement —
  leçon apprise en Sprint 3.

  Logging : chaque action critique est tracée —
  connexion réussie, échec de connexion, inscription,
  réservation, annulation, suppression. Avec l'adresse IP.
  Niveau INFO pour les actions normales,
  WARNING pour les suppressions et déconnexions.

Résultat Bandit final : zéro issue HIGH, zéro MEDIUM.

→ Diego, tu prends sur l'architecture finale ?

─────────────────────────────────────────────────────────────
  SLIDE 6 — ARCHITECTURE FINALE                    [DIEGO ~3 min]
─────────────────────────────────────────────────────────────

Merci. Là je vais vous montrer où on est arrivés
en termes d'architecture.

On a structuré l'app avec des blueprints Flask.
C'est le pattern de modularisation de Flask —
chaque domaine fonctionnel a son propre module isolé.

  pages_bp : toutes les routes HTML.
    Catalogue, détail livre, formulaire ajout/modification,
    connexion, inscription, déconnexion.
    C'est ce que voit l'utilisateur final.

  admin_bp : le panel d'administration.
    Gestion des utilisateurs, promotion admin,
    suppression de comptes, liste des livres côté admin.

  livres_bp, auth_bp, reservations_bp : routes API JSON.
    Utilisées par la suite de tests,
    et potentiellement par une future app mobile.

Côté base de données : SQLite via SQLAlchemy.
Deux modèles :

  Livre : titre unique, auteur, année de publication,
    disponibilité, champ created_by pour savoir
    qui a ajouté le livre — ça permet à chaque user
    de modifier uniquement ses propres livres,
    sauf les admins qui peuvent tout.

  User : email unique, hash du mot de passe, rôle.
    La propriété is_admin est calculée dynamiquement
    depuis le champ rôle — pas de flag booléen séparé.

Pour le frontend : Tailwind CSS v3 via CDN, sans framework JS lourd.
Composants custom : lightbox pour zoomer les couvertures de livres,
modales de confirmation pour les suppressions,
spinners animés sur tous les boutons de soumission.
Tout ça géré en JS vanilla dans le template de base —
un seul endroit, ça s'applique partout automatiquement.

Upload d'images : Pillow compresse automatiquement
les couvertures uploadées. Y'a une validation du type MIME
côté serveur pour éviter les uploads malveillants.

  SLIDE 7 — DÉPLOIEMENT & TRANSITION DÉMO          [RUDY ~1.5 min]
─────────────────────────────────────────────────────────────

Ouais. Deux mots sur le déploiement avant la démo.

L'app est déployée sur Render.com.
On a un fichier render.yaml dans le repo,
gunicorn comme serveur WSGI en production.
La SECRET_KEY est injectée comme variable d'environnement —
elle ne touche jamais le code source.

La base de données est SQLite.
Pour un projet démonstratif c'est suffisant,
et on est conscients que pour de la vraie prod
on passerait sur PostgreSQL avec un volume persistant.

Maintenant on va vous montrer tout ça en action.

Voilà pour la démonstration. En conclusion.

On est partis d'un script Python sans sécurité,
sans tests, sans interface utilisateur.
On a livré une application web complète :

  ✓ Authentification sécurisée Flask-Login + bcrypt
  ✓ Protection CSRF sur tous les formulaires HTML
  ✓ Logging complet des actions critiques
  ✓ Panel d'administration
  ✓ Interface responsive Tailwind CSS
  ✓ Upload et compression d'images
  ✓ 84 tests automatiques, 85% de couverture
  ✓ Zéro vulnérabilité Bandit HIGH ou MEDIUM
  ✓ Déployé sur Render.com

Les leçons qu'on retient de ce projet :
  La sécurité, ça se construit par itérations, pas en une fois.
  Les tests, c'est ce qui nous a permis de refactoriser sans casser.

Si le projet continuait, on verrait :
  Une CI/CD GitHub Actions pour lancer les tests
  automatiquement sur chaque PR.
  Du Docker pour standardiser le déploiement.
  Une base de données persistante en production.

─────────────────────────────────────────────────────────────
  ÉTAPE 4 — TEST CSRF EN LIVE                      [ARES ~2 min]
─────────────────────────────────────────────────────────────

Là je vais vous montrer ce qui se passe si quelqu'un
essaie de faire un POST sans token CSRF valide.

[Ouvrir la console DevTools, faire un fetch POST sans token]

  fetch('/catalogue/MonLivre/reserver', {
    method: 'POST',
    headers: { 'Content-Type': 'application/x-www-form-urlencoded' }
  }).then(r => console.log(r.status))

Vous voyez — 400 Bad Request.
Flask-WTF rejette la requête immédiatement.
Un site malveillant qui essaierait de faire des actions
au nom d'un utilisateur connecté récupère juste un 400.
C'est exactement le rôle de la protection CSRF.
